# Scoped Settings acceptance qualification

The six equivalent Apple preference names are already merged. This harness adds one actual Settings credential lifecycle case to each existing Mac/iOS UI bundle and one Mac fixture-isolation unit case. **All three new Swift cases are unexecuted until their native CI receipts exist.** Synthetic fixture success does not prove real-provider authorization, protected-data failure handling or cross-device sync. #1116 remains open until the approved acceptance is evidenced.

The cases display Alibaba’s row, reject missing/invalid local configuration, recover with valid configuration, save/replace a synthetic key, relaunch to inspect readiness, remove it and inspect readiness after another launch. Alibaba validation only parses its configuration, and its balance support is a billing link; the harness never records or starts a provider request. It must run with no other stored credentials. The validation error is the existing UI error contract. iOS Keychain write/remove failures currently log; this harness does not claim a new error presentation or hide that limitation. The displayed Stored/Replace state and relaunch check prove observed UI readiness, not the exact stored replacement value. Existing loading/update/removal/failure unit tests remain separate evidence. A relaunch failure must be investigated, not excused by a sleep or optimistic in-memory status.

Mac admission skips non-DEBUG UI configurations before app construction/launch, because its isolation requires the existing DEBUG-only CoreJourney bootstrap. Mac isolation uses that explicit UUID profile: separate settings/data/vault, no legacy vault import, encrypted key sync off and microphone permission denied. The two Alibaba @AppStorage configuration values read UserDefaults.standard, so the test supplies strings through each child process’s launch arguments and never edits those controls. Each relaunch replaces the whole argument list. Cleanup terminates only its app and removes only its UUID service (including its Alpha namespace), defaults and directory, without reading key values and requesting noninteractive Keychain cleanup.

iOS qualification requires a fresh job-owned Simulator before app construction or launch. The suite decodes the nonsecret job receipt propagated through Apple’s documented TEST_RUNNER_ environment contract and requires its created UUID to match CoreSimulator’s SIMULATOR_UDID, plus valid version/owner/configuration. Missing, malformed or mismatched admission skips without touching the app; the strict CI validator rejects that skip as qualification. Actual runner-environment propagation remains unexecuted until hosted native CI. A manual invocation on an existing personal Simulator without this explicit owned receipt cannot launch the credential fixture. The existing CI runtime/device selector is preserved as a configuration choice: the helper creates a new device with that exact installed runtime and device-type identifier. Its receipt records only the created UUID and configuration, bound to the current run/attempt/job. Creation never adopts an existing UUID. The always-running cleanup checks that ownership against the full device inventory (including unavailable devices), shuts down/deletes only that new device, verifies its absence and records the cleanup result; it never erases a pre-existing app or uses shutdown/delete-all. No developer phone, shared Simulator or signed-in app is an acceptance target. Real-device UI bundles skip this credential fixture and cannot satisfy its required CI suite. All three Simulator UI suites use a shared test-only launch helper: after the root appears it allows bounded arrival of first-run onboarding, taps the actual Skip control when present, and requires dismissal to a hittable Settings/record control. It never taps Allow Access or starts onboarding audio; existing tests do not depend on another case having completed first launch.

The Mac CoreJourney selector and iOS evidence validator require SettingsCredentialUITests. Missing, renamed, failed or skipped Settings suites cannot produce acceptance. Existing job runner labels, time budgets, build/test targets, cache and concurrency remain unchanged. Non-native simulator-command and coverage-parser regressions do not establish that simctl creation or either UI case ran successfully. Retain exact source/tested-merge, case status/count, owned-device receipt, log and cleanup result when qualification eventually runs. No local native execution or extra CI dispatch is required by this document.
