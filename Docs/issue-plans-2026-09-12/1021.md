# #1021 implementation plan: bounded await for an identified local capture

Decision: NARROW, SOL medium. Extend existing speak CLI/MCP/local automation transport. First scope is a named active Mac dictation, not arbitrary future History arrival or phone/watch relay. No Send to Mac, clipboard polling, CloudKit modification or new listener. Preserve explicit local Automation opt-in and existing same-user socket permissions.

## Attribution and cursor contract

A cursor proves order, not which transcript the caller intended. Require `capture_id` for await_transcript in the first release. Return that ID additively from successful start_dictation and active status, using MainManager.activeSession.id. The caller starts or deliberately identifies a local capture, then registers the wait before its completion; the user can stop via the existing hotkey/UI or a separate command. No automatic recording starts when awaiting. CLI syntax is `speak await --capture-id <uuid> [--since-id <history-uuid>] [--timeout <seconds>]`; MCP uses capture_id, since_id and timeout_seconds. Explain that unnamed “next phone transcript” is not implemented.

After initial History load/migration completes, atomically validate that capture_id is the current local capture and has not already appended a result, establish the current append revision and subscribe without an intervening suspension. A completion racing subscription either registers before the append and is observed, or fails registration as already complete; it never returns an older row. Default timeout is 60 seconds, allowed finite range greater than zero through 600; server validation enforces this independently of CLI. Invalid, missing, unrelated or already-completed capture IDs fail deterministically rather than attaching to whatever starts next.

Optional since_id must be a valid existing History UUID at registration; unknown/deleted identifiers fail. It identifies the caller’s known baseline only, not a request to replay entries between that row and registration. No insertion already present at atomic registration can satisfy this await. Use an internal monotonic append revision with server-instance epoch rather than dates or sorted History positions; no need to expose a new persisted global sequence in this first scope. Do not promise resumability across app restarts.

Multiple waiters explicitly naming the same capture may each receive its result: that is intentional fan-out. Waiters naming another capture never receive it. The first qualifying event after each waiter’s cursor must be a nonempty successful result for the exact registered local capture. Empty/cancelled/failed capture settles as a safe failure; it must not wait for the next recording. CloudKit backfill, manual imports, edits/polish updates, loading and unrelated local append events cannot qualify even if they are newest.

## Protocol and History seam

Edit Sources/SpeakCore/AutomationProtocol.swift additively: AutomationCommand.awaitTranscript raw value await_transcript; optional request captureID/sinceID; optional result captureID and one existing AutomationHistoryEntry result. Preserve all previous raw values and exported initializer signatures through forwarding overloads. Do not repurpose profile/provider/path. Keep schema version unless actual old-payload compatibility requires a change; old clients’ existing commands must still decode. New-client/old-server unsupported-command errors should be actionable, never mistaken for a successful empty result. Bound identifiers, payload and wait count (initially 16 concurrent underlying waits) and reject excessive waits without affecting status/stop.

Add a focused MainActor `AutomationTranscriptWaiter` beside AppAutomationHandler. Observe History append through an additive token-based subscription API; do not overwrite HistoryManager.onItemAppended, which already has a consumer and also fires in replacement/reload paths. Add an explicit local-capture completion origin/capture ID to the narrow new observer event or publish from the actual MainManager completion path tied to the append. Trace MainManager.swift and MainManager+SessionDiagnostics.swift call sites; only successful local final-result creation supplies this origin. MacHistorySyncAdapter remains remote and excluded. Preserve existing callback behavior and WAL writes.

Deliver the exact identified HistoryItem projection with the existing AppAutomationHandler.transcript(of:) policy at that insertion; later polish/edit does not produce a second result or change cached output. Inspect appendToWAL error semantics: append callback alone is not a new durability guarantee. Reuse existing failure evidence and describe output as captured local result without claiming cloud sync or forced disk flush. Never bypass History recovery safeguards to make await complete.

## Deadlines, cancellation and idempotency

AutomationServer currently keys completed/inFlight by request ID and command and returns an independent AutomationDeadline race while some operations continue. Await must own a bounded underlying lifetime too: a client deadline must unregister it, not leave a subscription until a later capture. Keep deadline start fixed on first acceptance; reconnect does not extend it. Result-versus-timeout settlement is exactly once using a monotonic clock and an explicit deadline tie rule (completion processed at/after deadline loses). Cancel subscription/task on app shutdown or Automation off.

For await only, retain a normalized request fingerprint with idempotency state: same request ID plus same capture/cursor/timeout joins/replays; reuse with changed arguments fails invalid_argument rather than replaying another capture’s text. Preserve existing other-command semantics. Cached terminal timeout/failure remains terminal; a fresh wait needs a new ID and still-active capture. An app restart resets the epoch/cache and cannot resume an old wait.

Track transport connection subscribers for a shared in-flight await. On last disconnection cancel the underlying wait; losing one of two identical retry connections must not cancel the other. A reconnect after cancellation receives the cached terminal disposition when retained, not a new capture subscription. Add real EOF/disconnect observation to the wait socket lifetime rather than assuming a failed future write cleans up. Existing deadline behavior for transcribe/start/stop is outside this change. CLI Ctrl-C/EOF cancels its connection promptly; no explicit new global cancel verb is needed.

## CLI/MCP concurrency and tests

Update CLIRunner and its actual argument parser, UnixSocketAutomationClient, MCPRequestHandler tool schema and Docs/automation.md. Text output prints the matched transcript, JSON/structuredContent includes exact History/capture identity. Keep provider credentials app-owned. #656’s MCP request IDs remain process-scoped; no claim of exactly-once retries across a new MCP process.

MCPStdioServer is currently blocking/single-threaded. A 600-second await must not prevent that same client from issuing stop/status or cancellation. Keep framing reader and stdout response writes serialized, dispatch await work through a bounded worker, and preserve ordering of existing mutating start/stop commands. Correlate every out-of-order completion by original JSON-RPC ID. Honor MCP cancellation for the identified await, EOF teardown and message-size bounds. Do not parallelize all mutating tools indiscriminately. Reuse the cancellable socket seam; a Task wrapper around a blocking uncancellable send is insufficient.

Extend AutomationServerTests/AutomationDeadlineTests, CLIBehaviourTests/MCPServerBehaviourTests and AutomationTransportTests with controlled append/deadline/EOF events. Cover atomic subscription race, preexisting/history-load/backfill/edits, failed/silent capture, independent simultaneous waiters, same-capture fan-out, request-ID mismatch, reconnect before/after cancellation, off/on epoch, shutdown, 600 bound and waiter-cap cleanup. Exercise actual framed socket and stdio: pending await plus status/stop on the same MCP stream must respond correctly without interleaved bytes. Test new fields decoding absent in old requests/results and all existing verbs unchanged.

Native Apple lint/build/core/app/automation tests and public API checks must pass. Then use actual installed standalone speak CLI and actual MCP client against an authorized running Mac app with a non-sensitive local capture: register await, stop recording, verify exact text/ID and timeout/cancel behavior. No live paid provider is needed if installed local speech is available. Do not publish transcript logs. Phone/watch support stays unqualified until explicit freshness/capture attribution and actual CloudKit arrival are separately demonstrated. No release dispatch, Stable promotion or restored transport is authorized.
