# #1122 implementation plan: Swift 5 complete-concurrency diagnostics

Decision: NARROW; SOL medium. One configuration/evidence PR, not a Swift6 language migration. Enable complete checking for owned Swift targets, obtain a reproducible Apple diagnostic baseline and keep XCTest/runtime behaviour intact. Read reviews/1122.json, AGENTS.md and actual current Package.swift/Project.swift after #1120/#1123 integration. No blanket Sendable annotation, semaphore deletion, default-MainActor setting or test-framework policy change.

## Minimal configuration

Keep root tools version5.9 and explicitly set package `swiftLanguageVersions: [.v5]` using that manifest API. Apply `.enableExperimentalFeature("StrictConcurrency")` to every owned regular/executable/test Swift target, preserving existing per-target flags and avoiding duplicate SpeakCore settings. Use a small common settings constant or a manifest target loop restricted to source target kinds; binary/system/plugin targets are not Swift source compilation targets. Do not append settings to CTranscribe if #1120 has not landed. Do not alter third-party dependency manifests, resolved pins, Tooling's external SwiftLint graph or Tuist's own manifest interpreter.

The official [Swift migration guide, Enable data-race safety checking](https://www.swift.org/migration/documentation/swift-6-concurrency-migration-guide/enabledataracesafety/) documents enableExperimentalFeature for tools5.9/5.10. This existing syntax is sufficient; the issue's tools6 upgrade and enableUpcomingFeature sample are unnecessary for warnings-only coverage. Verify the exact manifest API and compiler invocation on the selected Apple toolchain rather than treating a tools-version bump as harmless. Compiler version and language mode are different dimensions.

Include the isolated benchmark package's owned targets if #1120 has landed, and dependency-free SpeakWatchCore if #1123 has landed, preserving their explicit Swift5 mode. Keep this coordinated small manifest edit separate from target relocation. `Tooling/Package.swift` currently has no owned Swift source targets, so no linter dependency migration is warranted.

In `Project.swift`, define or reuse one small base settings dictionary with `SWIFT_VERSION = 5.0` and `SWIFT_STRICT_CONCURRENCY = complete`, then merge it into actual macAppSettings, iosAppSettings, watchAppSettings, watchWidgetSettings, iosKeyboardSettings, iosShareSettings, iosWidgetSettings, iosTestSettings and any separately configured owned test/utility target. Preserve inheritance, active compilation conditions, feature flags, signing and deployment settings. Audit the final generated targets, including the inline settings block near the end of Project.swift, rather than assume adding one top-level dictionary reaches all targets. SwiftPM product settings and Xcode target settings are separate; verify both. Do not add warnings-as-errors or mute concurrency warnings.

## Diagnostic baseline and expansion stop

Record xcodebuild -version, xcrun swift --version, selected developer directory, build configuration, feature flags, commit and commands. Run a before/after build comparison on the same Apple toolchain/configuration where feasible, with clean task-specific derived/build paths so cached compilations do not hide warnings. Capture raw build logs and xcresult artifacts; count unique primary concurrency diagnostics by module, source location and diagnostic message, separating repeat emissions and notes. Distinguish existing warnings, newly exposed concurrency warnings and third-party warnings. A blanket `grep warning | wc` is not a meaningful per-module baseline.

Provide a concise baseline table in the PR or a small `Docs/strict-concurrency-baseline.md`, linking raw CI evidence: target/platform/configuration, owned files compiled, unique concurrency warnings, errors and command. Zero warnings is valid only for a target whose source was actually compiled. macOS building an `#if os(iOS)`-empty target is not iOS coverage. A skipped watch/extension target is reported as not built, not zero.

Run real macOS app/library/CLI/test source compilation and native iOS app/library/test targets. Generate simulator builds with the existing keyboard/share/watch feature flags enabled, including widget/complication targets; use repository commands/schemes and discover installed destinations rather than inventing scheme names. Do not change provisioning or release flags. Include Debug and required Release paths as existing CI dictates. Preserve approved native-runner SHA selection and ordinary required job names.

If the change reveals approximately more than150 new owned concurrency diagnostics, publish the baseline and stop expansion. Do not start fixing the app or switch modules to Swift6 to finish a checkbox. If even Swift5 checking produces errors, distinguish unsupported setting syntax/mode leakage from real compiler diagnostics; fix configuration mistakes, then report remaining errors as a concrete separate scope. Small follow-up module migrations should be chosen from measured counts and dependencies, not the ticket's assumed ordering alone.

## Verification and protected behaviour

Static manifest inspection tests may assert explicit mode/checking for owned source targets and absence on binary targets, plus generated Tuist build settings. These should verify final target configuration, not duplicate a list that can silently miss a new target. Native compiler output is the definitive setting check. Run existing lint/build/tests and API compatibility; no public symbol changes are intended. Do not claim complete checking proves runtime race freedom.

Do not edit `HistoryManager.flushImmediatelySync`: its previous MainActor semaphore deadlock is already removed, and synchronous termination deliberately retains the WAL and guards startup. Changing it to fire-and-forget async work can lose final transcripts. Likewise, do not rewrite URLSession delegates, audio callback queues, NotificationCenter closures or @unchecked Sendable just to reduce a grep count. Those require per-boundary ownership analysis and existing recording/history tests in separate changes.

AGENTS.md currently specifies XCTest. Leave new/existing test policy and CONTRIBUTING unchanged; adopting swift-testing is independent. No physical recording smoke is necessary for a configuration-only patch if native builds/tests remain equivalent, but any unexpected runtime change expands scope and requires its relevant device gate. Publish exact unavailable Apple target coverage honestly; Linux can inspect manifests only. Submit a scoped conventional PR with baseline and explicit next-module proposals, not a claim that every target is Swift6 or semaphore-free.
