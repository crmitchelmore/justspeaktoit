## Composite contract and migration

Create `.github/actions/setup-apple-toolchain/action.yml`, composite, with only explicit `xcode-version` (empty means preserve current selected Xcode) and `install-tuist` (string true/false, default false) inputs. Keep current action version for maxim-lobanov/setup-xcode and existing brew installation mechanism/versions; dependency upgrades are separate. Validate Boolean-like values rather than rely on a nonempty 'false' string being false. Specify shell on run steps and use inputs context/environment safely; no arbitrary environment-map evaluation or command interpolation.

The [GitHub action metadata reference](https://docs.github.com/en/actions/reference/workflows-and-actions/metadata-syntax) defines composite steps and string defaults; JavaScript action pre/post lifecycle is a different schema. Do not add the issue's unsupported composite post-cleanup step, typed map input, ASC secret or keychain management. Final always() cleanup must remain at the workflow's end, not run when a setup composite finishes.

Migrate CI Tuist-install blocks with empty xcode-version so this refactor does not switch hosted CI away from its current default toolchain. Keep generation commands/flags and their current step conditions in each job. In release-ios.yml/release-appstore.yml, contiguous Xcode26.2 plus Tuist setup can become one composite call at the exact existing position. Their manifest configure/stamp, ASC key installation, upload-reuse preflight, conditional signing/profile validation, generation, copied Package.resolved and archive sequence remain unchanged.

release-mac.yml has intentionally separated setup: Xcode selection precedes Release tests on pristine tagged source; Tuist installation follows configure/stamp. Call the same small composite twice, once xcode-only with the existing receipt condition, once install-tuist-only with that condition. Combining them into one convenient early/late step would change ordering. Retain immutable manifest checkout, tests-before-stamp and restoring the frozen dependency lock exactly. Keep all signing/API-key/profile steps and final keychain/ASC cleanup text/conditions in their original workflow positions.

Do not add Apple toolchain setup to alpha-release.yml or prepare-stable.yml Ubuntu orchestration. Preserve ios-device-matrix.yml's hardware runner and specialised setup; adopt the helper there only for a genuinely identical existing Tuist/Xcode block, without changing device prerequisites. The success criterion is consistent shared behaviour, not zero textual Install Tuist occurrences or one setup step per workflow.
