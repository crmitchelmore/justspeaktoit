## Hypothesis and existing coverage

Current iOS SharedClientLiveTranscriber.startCapture calls startClient before startCaptureAudio/startAudioEngine. Modulate.start publishes the task and resumes synchronously; sendAudio rejects a missing/non-running task, then sends one initial WAV header. A no-start test exercises the wrong ordering. `TestLiveWebSocket` in `Tests/SpeakCoreTests/LiveWebSocketTestSupport.swift` sets running on resume and records messages in memory; it cannot establish URLSession's behaviour before HTTP upgrade.

Reuse #1130's `LiveWebSocketTransport`, `URLSessionLiveWebSocketTransport` and `LiveWebSocketFactory` for a narrow injection seam if Modulate needs one, preserving public initializers/options via forwarding overloads. An internal initializer may accept that existing factory. Production still constructs the same URLSession task/request and performs the same start/send/header/stop operations. Test factory may redirect the dummy-key request to a loopback endpoint and return the CONCRETE URLSession wrapper. A tracing decorator may record invocation state/time but must forward every operation to the real task; no fake socket, artificial running state or fake send completion is acceptable in the qualification run. Keep all application code changes to this seam, not presumed fixes.

Apple's [URLSessionWebSocketTask](https://developer.apple.com/documentation/foundation/urlsessionwebsockettask) and [task running state](https://developer.apple.com/documentation/foundation/urlsessiontask/state-swift.enum/running) references underpin the issue's existing observation: running is not handshake-complete, and pending sends can queue. The harness measures these separate events rather than inferring one from another. No numeric200–1000ms loss claim is established.

## Small real-server harness

Implement a local test peer that accepts TCP/HTTP upgrade but withholds the101 response until a test-controlled release signal. Prefer an existing proven test listener if its handshake can actually be held; the existing TransportLoopback tests are useful process/port-lifetime examples, not proof their transport matches this HTTP-upgrade requirement. Do not substitute delayed application messages after an already-completed handshake.

A concrete minimal Apple-host execution path is a Python3 standard-library helper in `scripts/tests/fixtures/delayed-websocket-server.py`, launched by a focused `Tests/SpeakCoreTests/ModulateHandshakeQualificationTests.swift` on macOS. It binds loopback only on port0, reports the selected port and 'upgrade request received' to the test via a separate bounded control pipe, waits for an explicit upgrade command, then performs a valid WebSocket handshake and records client binary messages. This uses a real Apple URLSession client and real TCP peer; Python is test infrastructure only, not an app/runtime dependency. Use the existing repository subprocess timeout/cleanup patterns; do not add a Python package or public server.

Implement only the needed bounded WebSocket server behaviour correctly: Sec-WebSocket-Accept from the request key, no negotiated compression, masked client frame decoding, length bounds, continuation assembly, ping/pong/close handling and exact payload recording. Follow [RFC6455](https://www.rfc-editor.org/rfc/rfc6455.html) sections4–5 rather than assuming one TCP read equals one frame. Unit-check its frame parser with split/coalesced input so an incomplete test peer cannot fabricate audio loss. Bound HTTP header size, message size, accepted connections and every wait. Report only synthetic run/chunk IDs, byte counts/digests and stage timings, never URLs/query credentials or user audio. All tests use a dummy credential.

The Swift test controls release through the peer's control pipe; avoid sleep-based 'probably still handshaking'. Observe actual URLSessionWebSocketDelegate.didOpenWithProtocol separately from task.state. Record start returned, each send invocation/state, upgrade request arrival,101 release, didOpen, send completion/error and server receipt. A held101 plus send invocations before release proves the intended pending-handshake condition.

## Scenarios and assertions

Generate deterministic PCM16 mono16kHz payloads with recoverable sequence tags in the sample bytes; include small and uneven chunks so comparisons are byte-based, not frame-count assumptions. Maintain a separate exact expected concatenation. Treat the WAV prefix as container bytes once, not PCM; validate RIFF/WAVE fields, channel/sample rate/format and single-header placement against actual Modulate.makeStreamingWAVHeader semantics.

Run the real Modulate start, immediately send synthetic chunks in the same serial order as iOS capture, hold upgrade while several chunks are admitted, release, then send more. Wait for server receipt of the expected byte total before calling the current abort-like stop, so shutdown loss cannot masquerade as startup loss. Compare exact bytes/order, zero gaps/duplication and exactly one WAV header. Record task.running and handshake pending as separate observations. Cases:

- Immediate upgrade control run.
- Explicitly held upgrade with PCM sent before101 and after101.
- Connection/upgrade failure with observed send/receive errors, separately classified from silent admission loss.
- Stop while handshake is held, then release: no delivery obligation after abort, and old work must not leak into a new run.
- Fresh start/restart with distinct PCM pattern and exactly one header for each new session.
- A before-start and after-stop send control, clearly labelled outside normal capture ordering; no claim that intentional discard there reproduces #947.

Use bounded XCTest expectations/continuations and teardown cancelling real tasks/session/child process/listener even after failure. A missing helper/blocked loopback is unavailable environment evidence, not a passing no-loss result. Do not use XCTestSkip for the designated qualification job and then claim the gate passed. Keep existing StreamingAudioPrerollTests; correct only misleading comments equating 'no start' with handshake delay if touched, preserving their actual buffer assertions.
