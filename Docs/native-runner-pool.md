# Reviewed native runner pool

The `build-macos` and `api-compatibility` CI jobs can use `[jsti-macos-build, macOS]`. The pool is opt-in for one reviewed revision via the repository Actions variable `JSTI_NATIVE_APPROVED_SHA`. An unset or nonmatching value retains GitHub-hosted routing.

For a pull request, the source repository must be this repository and the variable must match its exact head SHA. Fork pull requests never match this route. For a push, only `refs/heads/main` with its exact commit SHA can match. Labels and this variable are scheduling controls, not a security boundary: each Mac must independently enforce its local admission policy before any job step runs.

Before activating a revision:

1. Review the source and workflow. Confirm native architecture support and the checkout revision; do not execute arbitrary fork code.
2. Configure both Mac admission hooks for the exact intended revision/event/jobs, including the PR base and merge revision where required. The laptop defaults to rejecting all PR events; merely setting this variable does not enable its hook.
3. Verify both registered runners are online and carry `jsti-macos-build` and `macOS`. Retain their accurate X64/ARM64 labels. Do not assign ARM64 to the Intel laptop.
4. Set `JSTI_NATIVE_APPROVED_SHA` to the reviewed source SHA, then start a fresh CI run and verify its named runner and hook acceptance. A rerun of an existing job may retain its original routing.
5. Clear the variable to return future jobs to hosted routing. Changing a source revision requires a fresh admission review and matching configuration.

Build cache keys and restore prefixes include `runner.arch`, a stable host identity (runner name for self-hosted machines, `hosted` for GitHub-hosted machines), and `github.workspace`. The lint tooling build cache uses the same isolation. This keeps Intel/ARM object files separate and prevents absolute-path build state from crossing checkout locations. The laptop uses one shared build slot across repositories, nine Swift build workers and reduced process priority. Its CI menu can pause both laptop runners; pausing may cancel active jobs. These controls do not provide a hard CPU/RAM quota or sandbox untrusted code.

## Hosted capacity fallback

`ci.yml` uses the standard GitHub-hosted `macos-26-intel` label for ten Apple lanes: Debug, Release, public API compatibility, lint, standalone iOS SwiftPM compilation, iOS test-product compilation, iOS app tests, keyboard/watch device builds, core-journey contracts and launched fixture UI. GitHub's [runner image catalogue](https://github.com/actions/runner-images#available-images) documents this x64 label separately from paid `-large` runners. Its [image inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-Readme.md) supplies macOS 26 and Xcode 26, retaining the OS/SDK generation of the ARM `macos-latest` route. This avoids the ARM pool's repeated five-attempt acquisition failures without enabling the native pool or weakening any build/test gate. Existing native guards, path conditions and job timeouts are retained; both new compiler jobs are hosted-only and additionally required by the protected aggregate.

The default full Apple package graph is not architecture-selected. iOS/watchOS/keyboard device builds still cross-compile for their device architectures; simulator tests run the Intel simulator slice. Core-journey contracts and launched fixture tests use native macOS destinations, not an ARM-only executable. Fresh hosted x64 CI, including the full Debug/Release suite and fixture/iOS execution evidence, is the acceptance gate; prior Intel success is supporting evidence, not a substitute.

Compilation and simulator execution have separate thirty-minute budgets. The compiler generates the shipping keyboard/app project without booting a simulator, then uses Apple's `build-for-testing -testProductsPath` to export the complete unit/UI products. Both simulator architectures are built so the historical ARM native route is not given an Intel-only executable. The runner downloads the compiler's immutable artifact ID, verifies the checkout revision and exact Xcode/SDK versions, restores executable permissions and relative links, then uses `test-without-building -testProductsPath` with the same complete target selection. No compiled object cache is shared between hosts.

Simulator readiness is a bounded owned `simctl bootstatus -b` process, with at most ten minutes inside the unchanged thirty-minute execution job; compilation and package resolution no longer compete with boot. Timeout/nonzero results fail explicitly and terminate/reap only that process. Complete XCTest execution evidence remains mandatory. The plain test log is uploaded separately, so an unfinished `.xcresult` directory cannot prevent retaining the log.

Hosted run [37667732522](https://github.com/crmitchelmore/justspeaktoit/actions/runs/37667732522) demonstrated why overlap alone was insufficient: standalone SwiftPM compilation plus project generation consumed nineteen minutes, leaving too little time for the complete simulator suite. All 547 unit tests and three Action Button UI tests passed, but the job reached its overall thirty-minute limit during capture-flow UI tests; watch builds were not executed. The revised workload partition keeps the same standalone SwiftPM command in a separate thirty-minute, hosted-only job, and moves unchanged unsigned watch/containing-iOS builds into the keyboard device-build job (both keyboard shapes alone took eight minutes). The protected aggregate now requires the new SwiftPM job as well as the existing simulator and keyboard jobs, so failures, cancellations and skips cannot lose coverage. Fresh complete hosted acceptance of all three workloads remains required; partial test results are not a passing gate.

The combined-main run [37677443377](https://github.com/crmitchelmore/justspeaktoit/actions/runs/37677443377) still expired during the test command: project preparation took nineteen minutes even after standalone SwiftPM was removed (Tuist reported 975.695 seconds, including over ten minutes resolving Xcode packages). This motivates the explicit build-for-testing/test-without-building boundary, rather than increasing the overall job timeout or dropping UI tests. That run's API comparison was also incomplete after transient Sentry/Sparkle binary download failures; those are failed gates requiring a real retry, not established compatibility breaks or passing evidence. Fresh hosted acceptance of the distributed test-product path remains unproven.

Intel CI does not establish ARM-only local-model support or ARM runtime acceptance. Portable macOS, Windows cross-proof, local-transcription benchmark/model lanes and all release workers retain their existing ARM routing. In particular the macOS release worker must still launch its ARM64 candidate on an ARM host. CodeQL's hosted fallback is unchanged: the observed compiled/analyzed run failed at upload, so moving its compiler host is not a fix for that failure. Existing native source guards (including the historical owner-approved PR route) are unchanged; no runner registration, admission hooks or repository variables are altered.
